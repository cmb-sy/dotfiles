# generate-problem — distill の中身から問題を出す

distill に溜めた知識を、自分で選んだテーマについて問題にして解き、採点と解説を受けて残す。

**問うのは、生成 AI が実装を担うほど人に求められる素養。** 実装の速さや正確さは AI が担うようになる。その分、人が持ち続けなければならない判断（何を作るか・どの制約を優先するか・AI の出力のどこが危ういか）に寄せて出題する。

**開始時アナウンス:** 「generate-problem を開始します。」Step 1 で入力が決まったら、テーマ・問題数を明示する。

## Step 1: 入力を決める

**入力はすべて AskUserQuestion の選択肢で聞く。** 引数（ユーザーの最初の依頼）で指定された項目は聞かず、**足りない項目だけ**を聞く。**難易度は選ばせない**（混ぜて出す）。

### テーマ（最初に聞く）

Q1「どこから出しますか？」

| 選択肢 | 次に聞くこと |
|---|---|
| 学習メモ全体 | なし |
| 学習メモの分類から選ぶ | Q2 で `$HOME/develop/distill-vault/学習メモ/` の分類ディレクトリを出す |
| プロジェクトから選ぶ | Q2 で `$HOME/develop/distill-vault/プロジェクト/` のディレクトリのうち除外されていないものを出す |

Q2 の候補はその場で `ls` して作る（決め打ちしない）。材料の多い順（md の本数）に並べ、4 つを超える分は、AskUserQuestion が自動で足す「Other」で受ける。そのとき、残りの候補の名前を質問文に並べる。分類やプロジェクトの候補が 0 なら、Q1 のその選択肢を出さない。

### 問題数（テーマの後に聞く）

選択肢は 3・5・10 にし、それ以外の数は「Other」で受ける。形式は聞かない（すべて 4 択で出す）。問題数は 1〜20。範囲外なら範囲を伝えて聞き直す。

**除外の読み方:** 除外は `$HOME/develop/distill-vault/除外.md` に書かれている。`## プロジェクト` 見出しの下の箇条書き（`- <名前>`）が除外するプロジェクトのディレクトリ名、`## 記録` 見出しの下の箇条書き（`- <プロジェクト名>/<日時>`）が 1 件ずつ除外する記録（`プロジェクト/<プロジェクト名>/記録/<日時>.md`）。各行の末尾の `<!-- ... -->` は注釈なので取り除き、名前を囲む `[[ ]]`、末尾の `.md` と `/` も外して読む。ほかの見出しの下の行と、コメントだけの行は除外として扱わない。

引数でテーマを指定されたときは、候補への部分一致で解決し、2 つ以上に当たれば選択肢で聞く。除外されたプロジェクトに当たったら候補にせず、そう伝えて Q1 から聞く。どれにも当たらなければ Q1 から聞く。

## Step 2: 材料を集める

| テーマ | 材料 |
|---|---|
| 学習メモ全体 | `学習メモ/**/*.md` |
| 学習メモの分類 | `学習メモ/<分類>/**/*.md` |
| プロジェクト | `プロジェクト/<名前>/**/*.md` と、frontmatter に `project: <名前>` を持つ学習メモ |

**外すもの:** 問題集は公開サイトに出る正本に記録するので、出さないと決めたものを材料にしない（除外の読み方は Step 1）。

- 除外されたプロジェクトに frontmatter の `project:` で紐付く学習メモは材料から外す
- `## 記録` に書かれた記録のファイルは材料から外す

材料が 0 本なら「<テーマ> には材料がありません」と伝えて終わる。

## Step 3: 下読み（エージェント 1 体）

`general-purpose` エージェント 1 体に、材料のパスの一覧を渡し、材料を**すべて**読ませる。返させるのは次の形の素材表（YAML）だけにする。出題・採点・解説はメインが行う（材料をメインの会話に読み込まない。大きいテーマで会話が重くなるため）。

```yaml
- concept: <概念の名前>
  explanation: <正しい説明 2〜4 文。材料の記述に基づく>
  misconception: <よくある誤解 1 文。材料に無ければ空>
  aspect: 仕組み | 判断 | 壊れ方 | 大局
  era: 問題の定義と要件 | 設計の天秤 | AI の出力の検証 | 壊れ方と観測 | データの意味と品質 | 安全と統制 | なし
  source: <材料の md の題（本文先頭の # の行。無ければファイル名）>
```

エージェントへの指示に必ず含める:

- 材料に書かれていないことを足さない（推測で補わない）
- 構文・API の名前・コマンドのオプション・設定値は概念にしない
- 勤務先の会社名・顧客名・社内のシステム名・人名を素材表に書かず、一般的な言葉に置き換える。構成や数値は、判断の型を伝えるのに要る範囲だけ残す

素材表の概念が問題数より少なければ、1 つの概念から観点を変えて複数問作ってよい。

## Step 3.5: Web で補強する

出題に使う概念を素材表から問題数ぶん選んだら、概念ごとに Web で関連する情報を調べ、問題と解説に絡める。distill の材料だけだと、学んだ時点の知識に閉じる。最新の動向・実際に起きた障害・公式の説明を絡めると、知識が今の現場とつながる。

1. 概念ごとに `WebSearch` で 1〜2 回検索する。探すのは、公式のドキュメント・実際に起きた障害や事例・業界の動向・その概念を扱った信頼できる解説
2. 使えそうな結果は `WebFetch` で中身を読み、主張を確かめる。**確かめられなかった情報は使わない**（検索結果の見出しや要約だけで書かない）
3. 確かめた情報を、問題に絡める（例: 「実際に起きたこの障害は、どの設計の判断が原因か」）か、解説に添える

決まり:

- **問題の芯は distill の材料に置き**、Web の情報は補強に使う。自分が学んだことを確かめるスキルなので、材料から離れた問題にしない
- 使った情報には、解説の中で出典の URL を添える
- Web の情報が材料の記述と食い違ったら、どちらが正しいかを確かめられた範囲で解説に書く。確かめられなければ「材料と Web で食い違う（未確認）」と書く
- 検索の失敗や情報が見つからない概念は、材料だけで出題する（止めない）

## Step 4: 出題

### 問う素養（各問に明記する）

| 素養 | 問うこと |
|---|---|
| 仕組み | なぜそう作るか・何が起きているか |
| 判断 | どの状況で何を選び、何を失うか |
| 壊れ方 | どこで壊れるか・何を確かめるべきか |
| 大局 | 全体の中での位置・一般的なやり方との比較 |

### 優先する観点（AI の時代に人に要るもの）

素材表の `era` が「なし」以外の概念を優先して選ぶ。

| 観点 | なぜ人に要るか |
|---|---|
| 問題の定義と要件 | AI は頼まれたものを作るが、何を作るべきかは決めない |
| 設計の天秤 | どの制約を優先するかは、状況を知る人が決める |
| AI の出力の検証 | AI はもっともらしい誤りを自信のある文章で出す |
| 壊れ方と観測 | 壊れたことに気付けなければ、誰が作っても同じ |
| データの意味と品質 | 数字が正しく計算されても、定義が食い違えば判断を誤る |
| 安全と統制 | 誰が何を見てよいか・何を外に出してよいかは組織の責任 |

### 決まり

- **「AI が出したこの設計（答え）のどこが危ういか」を見抜く問題を 1 問以上入れる。** 問題文の中に、AI が出したという想定の短い答えを置き、危うい点を選択肢から選ばせる
- **問わない:** 構文・API の名前・コマンドのオプション・設定値の暗記・特定ツールの操作手順
- 難易度は混ぜる
- 選択肢はすべてもっともらしくする（明らかな外れを置かない）。誤りの選択肢は、素材表の `misconception` や Web で確かめた古い常識から作る
- 判断を問う問題は、記述させる代わりに「考え方」を選択肢にする（どれも一理あるが、最も筋が良いのは 1 つ）

### 問題文の書き方

問題文は本文に、次の 3 つの小見出しで書いてから、答えを AskUserQuestion で受ける。短い状況文と選択肢だけで出さない（目的は採点ではなく、判断できるエンジニアに育てること）。

1. **前提**: 登場する仕組みを、図（ASCII）や表で示す。用語は初出で一言定義する。読み手はそのテーマを初めて見る前提で書く
2. **状況**: 何が起きたか、AI が何と答えたか
3. **問い**: 何を考えてほしいかを 1〜2 文で示してから問う

選択肢は AskUserQuestion の `description` に収まる長さにし、収まらない説明は前提に回す。ユーザーが「〇〇とは？」と聞き返したら、答えを明かさない範囲で具体例を使って説明し、同じ問題を出し直す（記録に聞き返したことを残す）。

### 進め方

1 問ずつ出す。問題の見出しに `問 N / 全 M（<素養> / <観点>）` を置く。`era` が「なし」の概念から作った問題は、見出しを `（<素養>）` だけにする（記録の見出しも同じ）。答えを受けたら、**正解は見せずに次へ**進む（前の問題の解説が後の問題のヒントにならないようにする）。**答えは必ず AskUserQuestion の選択式で受ける**（本文に選択肢を並べてテキストで答えさせない）。

途中で「やめる」と言われたら、そこまでの答えで Step 5 へ進む。

「Other」に書かれた答えは、「やめる」なら中断、「〇〇とは？」なら聞き返しとして扱う。それ以外は記述の答えとして採点せず、A〜D から選ぶよう添えて同じ問題を出し直す。

## Step 5: 採点と解説（全問の後にまとめて）

解説は採点の添え物ではなく、**ユーザーを育てる教材**として書く。短くまとめるより、理解に要る段を省かないことを優先する。読み手がその概念を他人に説明できる水準を目安にする（1 問あたり 40〜80 行）。

問題ごとに、次の小見出しで書く:

| 段 | 書くこと |
|---|---|
| 問題 | **問題を再掲する**（前提の要約・状況・問い・選択肢 A〜D・あなたの答え）。解説を読む時点では何を問われたかを忘れているため |
| 結論 | 正解と、あなたの答えの正誤を 1〜2 文で |
| 前提の仕組み | 問題の前提を図か表で示し直す。用語は初出で一言定義する |
| なぜそうなるか | 因果を 1 段ずつ積み上げる。「だから」の間を飛ばさない |
| 具体例 | 小さな数値例や表で、手を動かして追える形にする |
| 選択肢ごとの検討 | **4 つすべて**について、なぜもっともらしいか・どこで外れるか（正解はなぜ最も筋が良いか）を書く。表にする |
| よくある誤解 | 誤解と、その誤解がどこから来るか（古い常識・名前からの連想・別の性質との混同など） |
| 実務での確かめ方 | 同じ場面に出会ったとき、何をどの順で確かめるか（手順、クエリやコマンドの形） |
| 同じ型が出る場面 | この問題の型が、ほかの技術や状況でどう現れるか 2〜3 例 |
| AI の時代に人が分かっている必要がある理由 | **なぜ AI の時代にこれを人が分かっている必要があるか**を 2〜3 文で |
| 出典と次に読むもの | 材料の md の題、Step 3.5 で使った Web の URL、次に読むもの |

**精度:** 主張ごとに根拠の出どころ（材料・Web で確かめた一次情報・推論）を区別する。推論は「〜と考えられる」と書き、断定しない。「〜できない」「〜が原因」は成り立つ条件を添える。

**会話での区切り:** 会話に出す解説は、問題ごとに次の 3 行で区切る（記録の md では `## 問 N` の見出しにする）。問題の中の各段は `────────── <段> ──────────` の小見出しで区切る。

```
────────── ────────── ────────── ────────── ────────── ────────── ────────── ────────── ──────────
────────── 問 N｜解答 ──────────
────────── ────────── ────────── ────────── ────────── ────────── ────────── ────────── ──────────
```

**見やすさ:** 1 文に 1 つの主張。要点は太字。5 行を超える段落を作らない。3 項目以上の比較は表、流れは図にする。

**弱点に合わせる:** 不正解の問題と、聞き返しがあった問題は、正解した問題より一段深く書き、具体例を増やす。

最後に全体のまとめ:

- 得点。正答数を `<得点>/<問題数>` で書く（途中でやめたときの分母は、答えた問題数）
- 素養ごとの出来（仕組み・判断・壊れ方・大局）
- 弱いところ（誤答に共通する読み落としの型を言葉にする）と、次に学ぶこと（読む材料の md を題で名指し、何を確かめながら読むかを添える）

## Step 6: 記録

`$HOME/develop/distill-vault/問題集/<テーマ>/<YYYY-MM-DD-HHMM>.md` に書く。`<テーマ>` は、学習メモ全体なら `学習メモ全体`、分類なら `学習メモ-<分類>`、プロジェクトなら `<プロジェクト名>` にする。ディレクトリが無ければ作る。`<YYYY-MM-DD-HHMM>` は出題を始めた時刻。同名のファイルがあれば `-2`、`-3` と番号を足す。

```markdown
---
date: YYYY-MM-DD
theme: <テーマ>
format: 4択
count: <問題数>
score: <得点>/<問題数>
---
# <テーマ>の問題 YYYY-MM-DD

## 問 1（<素養> / <観点>）
<前提・状況・問いの要約>

- A: <選択肢>
- B: <選択肢>
- C: <選択肢>
- D: <選択肢>

**あなたの答え**: <答え>
**採点**: 正解 | 不正解

<聞き返しがあれば、何を聞かれ、どう説明したかを 1 行>

<解説: 正解・評価・なぜ・誤解・AI の時代に要る理由・出典・次に読むもの>

## まとめ
<得点・素養ごとの出来・次に学ぶこと>

## 参照した Web の情報
- [<題>](<URL>) — 問 N で使った。何を確かめたかを 1 行
```

- **勤務先の名前と社内の作りを書かない**（一般化の範囲は Step 3 と同じ）
- **絶対パス（ホームディレクトリの実際のパス）を書かない。** `~/` に置き換える（distill のビルドが混入を検出すると公開ごと止める）
- 学習メモへは `[[題]]` でリンクしてよい。プロジェクトの md は題を文字で書く
- 途中でやめたときは、答えた分だけを採点・解説して記録し、frontmatter に `status: 中断` を足す。`count:` は実際に答えた問題数にし、`score:` の分母もそれにする。予定していた問題数は `planned: <予定の問題数>` で足す
- 1 問も答えていなければ記録を書かず、完了報告で「1 問も答えていないので記録していません」と伝える

完了報告は 2 行にする:

```
generate-problem 完了。<テーマ> <得点>/<問題数>
記録: distill-vault/問題集/<テーマ>/<YYYY-MM-DD-HHMM>.md
```

## Red Flags（やってはいけないこと）

- 構文・API の名前・コマンドのオプションを問う
- 材料に無いことを、推測で問題や解説に足す
- 1 問ごとに正解を見せる
- 難易度や形式を聞く
- 前提を書かずに、短い状況文と選択肢だけで出す
- 選択肢を本文に並べ、テキストで答えさせる
- 除外されたプロジェクトに紐付く学習メモを材料にする
- 記録に勤務先の名前・社内の作り・絶対パスを書く
- 材料をメインの会話に全部読み込む（下読みはエージェントに任せる）
- 中身を読んで確かめていない Web の情報を、問題や解説に使う
